# 博客交流协会：从静态目录到社区平台的托管与扩容调研

> **状态：下一阶段平台架构建议，不代表当前已实现、已部署或已购买服务。**
>
> 本文以 [v2 导航站设计](../design-v2.md) 为起点，并以平台愿景为范围：多作者拥有公开主页并发布内容；读者发现、关注和互动；成员按技能、方向与协作意愿寻找队友。配额与价格会变化；本次核对日期为 2026-09-16，采购前必须重查官方页面。

## 结论

这是内容与关系网络平台。容量首先受内容流读放大、互动写入、匹配检索、用户媒体，以及通知/RSS/审核等异步任务影响，而不是单纯账号数。

建议路线是：**静态目录不动 → 受管动态核心 → 拆 worker 与搜索 → 必要时拆 API 到独立服务**。不要因几十 DAU 就搬离 GitHub Pages；也不能在社交功能上线后把所有后续工作塞进一次 Vercel HTTP 请求。

公开运营起步时应采用 Vercel Pro 或功能等价的可计量付费层。Hobby 面向个人、非商业项目，达到硬上限通常无法购买超额用量，不适合作为平台生产承诺。[Vercel Hobby](https://vercel.com/docs/plans/hobby) [Vercel Pricing](https://vercel.com/pricing)

## 1. 当前目录与平台阶段的边界

| 能力 | 静态目录阶段（当前设计） | 社区平台阶段 |
| --- | --- | --- |
| 博客收录、技术栈、RSS 新鲜度 | `blogs.json`、GitHub Actions、GitHub Pages | 保留，作为公开索引的冷内容来源 |
| 个人主页 | 外链与作者字段 | 平台 profile、技能、项目经历、协作意向、隐私设置 |
| 发布 | 作者在各自博客发布 | 短动态、项目展示、招募帖；长文先继续以外链/RSS 聚合为主 |
| 发现 | 标签、技术栈、随机逛逛 | 关注流、话题、热门/最新、全文搜索、匹配候选 |
| 组队 | 不适用 | 结构化筛选、可解释匹配、双方同意的联系请求 |
| 治理 | 人工编辑与失联归档 | 举报、屏蔽、限流、审核队列、审计与数据保留 |

推荐的动态 MVP 不是完整站内博客或 LinkedIn 复刻，而是：认领主页、提交 RSS、填写协作卡、发布项目招募、按条件寻找成员、申请联系、屏蔽与举报。这既保留独立博客的开放性，也先验证“组队”是否真有需求。

## 2. 平台负载模型：先测行为，不只看 DAU

| 事件类 | 例子 | 主要消耗 | 风险 |
| --- | --- | --- | --- |
| 内容流读取 | 首页、关注流、话题、个人主页 | CDN、函数、Postgres、缓存 | 同一人每日多次刷新，通常是最大请求量 |
| 关系与互动写入 | 关注、点赞、评论、屏蔽 | 事务、索引、锁 | 一致性、重复写入、垃圾行为 |
| 发布与媒体 | 招募帖、头像、项目封面 | 对象存储、审核、图片处理 | 媒体不能塞入数据库行或函数临时文件 |
| 匹配与搜索 | 技术栈/城市/投入时间筛选 | 索引、全文检索、缓存 | 每次匹配扫全表会失控 |
| 异步任务 | RSS、通知、邮件、审核、索引 | 队列、worker、第三方 API | 不能阻塞发布/登录 HTTP 请求 |

从上线开始记录：内容流请求/DAU/日 `F`、互动写入/DAU/日 `W`、发布/活跃创作者/日 `P`、搜索或匹配/DAU/日 `M`、通知投递/互动 `N`。

```text
月内容流读取 ≈ DAU × F × 30
月互动写入   ≈ DAU × W × 30
月匹配查询   ≈ DAU × M × 30
```

例如 300 DAU、每人每天 15 次内容流读取、1.5 次互动、2 次筛选/匹配，约为 13.5 万次内容流读取、1.35 万次写入和 1.8 万次匹配查询/月。量本身不大，但若每次读取都做多表 join、全文模糊搜索和头像回源，免费配额与 p95 延迟会先恶化。

## 3. 推荐架构：静态发现层与动态社区核心分离

```text
公开访问者
  ├─ 目录、博客外链、介绍 ──────────> GitHub Pages / CDN（保留）
  └─ 平台主页、内容流、成员页 ──────> Next.js Web / API
                                             │
       ┌─────────────────────────────────────┼────────────────────────────────────┐
       ▼                                     ▼                                    ▼
PostgreSQL（事实源）                    Object Storage                       Redis / Queue
用户、内容、关系、申请                  头像、封面、媒体                    缓存、限流、异步投递
       │                                     │                                    │
       └─────────────────────────> Worker / Outbox <──────────────────────────────┘
                            RSS、通知、邮件、审核、搜索索引、匹配重算
```

### 数据库、内容流与匹配

- PostgreSQL 保存 `profiles`、`posts`、`comments`、`follows`、`projects`、`team_requests`、`blocks`、`reports` 与通知状态。短事务写入事实数据及 outbox；worker 再投递通知、写索引、重试失败任务。
- Neon Free 当前为每项目 100 CU-hours、0.5 GB 存储、5 GB 公网传输，并可闲置归零；公开平台应按 CU-hours、存储和出网，而不是用户数，决定何时升级 Launch。[Neon Pricing](https://neon.com/pricing) [Neon 网络传输](https://neon.com/docs/introduction/network-transfer)
- 早期关注流用 **fan-out on read**：按关注作者读取最新帖子、游标分页、短 TTL 缓存。只有高粉作者或热点流已造成实际瓶颈，才引入 worker 预计算的混合 timeline。
- 第一版匹配使用技能、主题、时区/城市、每周投入、招募角色、项目状态等显式条件。用 B-tree、GIN、全文检索与 trigram 索引；不在每个请求扫描全表做 embedding 相似度。匹配必须说明理由，且由用户主动发起联系。

### Redis、队列与对象存储

- Redis 只存缓存、限流、幂等键和短期游标，绝不作为关系或内容唯一副本。
- 队列/worker 处理 RSS、邮件、站内通知、媒体后处理、搜索索引、举报检查与重试。QStash Free 当前 1,000 条消息/日，付费按量约 $1/10 万条；重试也计投递，故消费者必须幂等并检查死信。[QStash Pricing](https://upstash.com/pricing/qstash)
- 头像、封面与媒体走对象存储，数据库保存元数据和 object key。Cloudflare R2 当前免费层为 10 GB-month、100 万 Class A、1,000 万 Class B 操作，公网 egress 免费；签名上传仍需校验 MIME、尺寸与权限。[R2 Pricing](https://developers.cloudflare.com/r2/pricing/)

## 4. 按稳定 DAU 与创作者规模的路线

稳定 DAU 指过去 28 天日均值；任一监控项先越线时提前升级。

| 稳定 DAU / 活跃创作者 | 主要范围 | 推荐组合 | 不应做的事 |
| --- | --- | --- | --- |
| 0--30 / 0--10 | 目录、RSS、邀请认领主页 | GitHub Pages + Actions；动态 PoC 用 Vercel + Neon Free | 不公开注册、站内发帖、私信或语义匹配 |
| 30--300 / 10--80 | profile、协作卡、招募、联系申请、基础关注 | GitHub Pages 保留；Vercel Pro + Neon Launch；对象存储；事务邮件 | 不把媒体放 Neon；不同步发通知；不无审核开放评论 |
| 300--1,000 / 80--300 | feed、评论、话题、搜索、站内通知、举报 | Vercel Pro + Neon Launch + Redis + queue/worker + 对象存储 | 不让 RSS/通知/审核跑在用户请求内；不每次 feed 全表 join |
| 1,000--5,000 / 300--1,500 | 多维匹配、项目协作、审核后台 | CDN 前端；API 与 worker 分别部署；托管 Postgres、Redis、搜索索引 | 不一口气迁数据库；不在单一 Web 进程跑 worker |
| 5,000--20,000 / 1,500+ | 热点流、更多媒体、搜索排序、运营治理 | 多实例 API/worker、队列、搜索、对象存储、读扩展 | 不按平均 DAU 加机器；按热点、峰值 RPS、写延迟压测 |
| 20,000+ | 高可用与成熟运营 | 多区域/多可用区受管服务、灾备与容量演练 | 不依赖单台 VPS 或人工恢复 |

### 30--300 DAU：公开 MVP 的正确收敛

1. 发布先限制为结构化招募帖和短动态；长文继续链接外部博客/RSS。
2. 联系采用站内申请，接收方同意后才展示联系方式；不先做开放私信。
3. 评论只对验证用户开放，具备频率限制、举报入口和必要时的人工审核。
4. 头像/封面直传对象存储，服务端只签发短时上传凭证。
5. 使用唯一约束与幂等键防止重复关注、申请、点赞和通知。

Vercel Pro 的调用、Active CPU、内存与传输需在 Usage 中按路由观察；不能沿用旧的固定函数额度认知。[Fluid Compute Pricing](https://vercel.com/docs/functions/usage-and-pricing) [用量管理](https://vercel.com/docs/pricing/manage-and-optimize-usage)

### 300--1,000 DAU：异步化是分水岭

一次发布可能同时更新帖子、作者活跃度、outbox、搜索索引、关注者通知和匹配候选。HTTP 请求只写入事实数据和 outbox，后续由 worker 消费。

必须补齐：游标分页（禁用高偏移 `OFFSET`）、`(author_id, published_at DESC)`/`(topic_id, published_at DESC)` 复合索引、通知聚合窗口、用户通知偏好、worker 幂等键、退避重试、死信检查、内容的软删除与审核状态。

### 1,000--5,000 DAU：按职责迁移，而非全站搬家

需要常驻 worker、分钟级调度、长任务、实时连接或中国大陆 API 低延迟时，优先顺序为：**worker → 长连接/API → 高负载读接口 → 数据库**。数据库最后迁移。Neon serverless driver 可用于 serverless 环境，但长事务和连接模型仍须审查；不可在每个函数调用中失控地创建长连接。[Neon Serverless Driver](https://neon.com/docs/serverless/serverless-driver)

## 5. 可执行的升级触发器

| 触发信号 | 窗口 | 行动 |
| --- | --- | --- |
| Vercel 任一核心资源预计当周期超过 70% | 7 天 | 按路由排查、缓存公共读、设置预算；在受限前升级/拆分 |
| Neon CU-hours、存储或出网超过 70% | 7 天 | 优化索引/查询，清理数据，评估 Launch 与读缓存 |
| 首页/关注流 p95 > 800 ms | 7 天 | 排查 N+1、索引缺失、大 OFFSET、跨区访问，先优化读模型 |
| 发帖或评论 p95 > 500 ms | 3 天 | 通知、索引、媒体处理迁至 outbox/worker；缩短事务 |
| 队列积压 > 15 分钟或死信持续增加 | 任意一天 | 修幂等、并发与失败任务；禁止无限重试 |
| 对象存储操作/流量超过免费层 70% | 7 天 | 缩略图、尺寸上限、缓存与生命周期策略 |
| 举报/垃圾内容上升或审核 SLA > 24 小时 | 任意一周 | 收紧发帖速率，补审核工具与信誉分层，而非先加机器 |
| 需要分钟级任务、长 worker 或实时连接 | 需求确认即触发 | 拆 worker/API；不依赖 Hobby Cron |

## 6. 独立服务与中国内地部署

| 运行方式 | 适用场景 | 优势 | 代价 |
| --- | --- | --- | --- |
| Vercel Pro + Neon（优先） | SSR、短 HTTP、早期平台 API | 运维少、自动扩缩 | worker/长连接边界、用量账单 |
| Railway/Render 受管容器 | 需要常驻 API/worker，不想管理 OS | Docker 部署、职责易拆 | 常驻成本；免费层不作生产承诺 |
| 腾讯云 Lighthouse | 用户在中国大陆、接受 Linux 运维、有常驻进程 | 资源流量打包、成本可预测 | 补丁、TLS、备份、告警、恢复均自负 |
| CVM + LB + 托管数据库 | 多实例、私网、复杂扩缩 | 网络和扩缩能力完整 | 架构、账单和运维复杂度高 |

Render Free 会在 15 分钟无入站流量后休眠，唤醒约一分钟，且不建议用于生产；免费 web service 也不能使用 SMTP 常用端口，因此不适合作为认证邮件或 worker 的生产基础。[Render Free](https://render.com/docs/free)

腾讯云 Lighthouse 的中国内地示例套餐（本次查看）为：2 核 2 GB/40 GB SSD/3 Mbps/200 GB 月流量约 45 元/月；2 核 4 GB/100 GB SSD/7 Mbps/1,000 GB 月流量约 100 元/月；4 核 8 GB/180 GB SSD/12 Mbps/2,000 GB 月流量约 245 元/月。价格与可购规格会变，应以下单页为准。[腾讯云 Lighthouse](https://cloud.tencent.com/product/lighthouse)

中国内地服务器对外提供网站/App 时，域名须先完成 ICP 备案；更换接入商还需接入备案。香港实例不需要 ICP 备案。备案要在区域决策时作为前置依赖，腾讯云说明中管局审核最长可达 20 个工作日。[是否需要备案](https://cloud.tencent.com/document/api/243/19630) [接入备案](https://cloud.tencent.com/document/product/243/43878) [备案审核](https://cloud.tencent.com/document/faq/243/19650)

## 7. 平台上线前的治理与隐私基线

1. 公开 profile、私密联系方式、招募帖可见范围和后台权限必须分开建模；所有读取按所有者/可见性授权。
2. 注册、发帖、评论、关注、联系申请、上传、举报分别限流且有幂等策略；IP 不能是唯一防线。
3. 举报、屏蔽、软删除、审核状态、管理员审计日志和申诉路径需同时有数据模型与运营流程。
4. 服务端验证上传 object key、大小、MIME、实际图片内容和访问权限。
5. 通知必须有用户偏好、聚合窗口、关闭/退订和失败重试；不能将每次互动都邮件化。
6. 上线前定义账号删除、内容导出、举报证据保留、备份和恢复边界。

认证邮件应使用有清晰额度与投递 webhook 的事务 provider；QQ SMTP 可试验，但不应成为公开平台唯一通道。Resend Free 当前为 3,000 封/月且每天 100 封，Brevo Free 当前为每天 300 封；必须以真实 QQ、163、Gmail、Outlook 的小流量送达测试作为准入依据。[Resend Pricing](https://resend.com/pricing?product=marketing) [Brevo Free 限制](https://help.brevo.com/hc/en-us/articles/208580669-FAQs-What-are-the-limits-of-the-Free-plan)

## 8. 建议分期与独立验收

| 阶段 | 范围 | 通过条件 |
| --- | --- | --- |
| S0：目录可信度 | RSS、数据校验、失联归档、静态 SEO | 目录无需登录即可稳定发现博客，RSS 失败不破坏列表 |
| S1：成员认领 | 邀请注册、profile、协作卡、隐私设置 | 用户只能修改自己的资料，公开/私密字段正确隔离 |
| S2：项目与招募 | 项目页、招募、筛选、联系申请、屏蔽/举报 | 联系经接收方同意，重复请求幂等，有审核记录 |
| S3：内容与关系 | 动态、关注、评论、通知、基础 feed | 发布不被通知/索引故障阻塞，feed 有索引与游标 |
| S4：匹配与运营 | 可解释匹配、搜索、审核后台、worker | 匹配理由可见且可关闭，屏蔽/举报立即生效 |
| S5：扩容 | 独立 worker/API、缓存、容量演练 | 完成压测、告警、回滚和恢复演练 |

## 9. 当前建议

1. 保留并完成 `docs/design-v2.md` 的静态目录能力，它是平台公开入口和冷启动内容资产。
2. 动态 MVP 只做认领资料、协作卡、项目招募、联系申请、举报/屏蔽，不先做完整 LinkedIn 或站内长文系统。
3. 公开 MVP 起步即选择可观测、可支付的 Vercel Pro + Neon Launch 或等价组合；GitHub Pages 只托管静态发现层。
4. 内容流、评论和通知上线前，先建立 outbox + queue + worker。
5. 当常驻 worker、频繁调度、实时连接或中国大陆动态延迟被真实数据证明是阻碍时，先拆 worker/API，再评估 Lighthouse 或受管容器；数据库迁移最后进行。
6. 所有迁移以可回滚、数据不丢失、静态目录始终可访问为验收底线。
